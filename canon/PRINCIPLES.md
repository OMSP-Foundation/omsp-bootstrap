# OMSP Principles

## 1. Purpose

These principles define how OMSP work should be designed, governed, reviewed, and evolved.

They provide a stable reference for downstream artifacts, engineering standards, governance decisions, architecture decisions, and Work Package execution.

## 2. Principles

### 2.1 Knowledge First

Operational knowledge is a primary engineering asset. OMSP work should make knowledge explicit, structured, reusable, and governed.

### 2.2 Open by Default

Foundational artifacts should be public and reusable unless there is a documented reason for restriction.

### 2.3 Architecture Driven

Material implementation should be guided by architecture, models, and documented decisions rather than ad hoc execution.

### 2.4 Evidence Based

Claims, approvals, baselines, releases, and governance decisions should be supported by traceable evidence.

### 2.5 Automation by Default, Accountability by Design

Automation should reduce repetitive work and improve consistency, but accountability remains with named human roles, councils, or governance bodies.

### 2.6 Traceability by Design

Issues, artifacts, branches, commits, PRs, reviews, decisions, baselines, and releases should remain connected through explicit traceability.

### 2.7 Models Before Code

OMSP should clarify concepts, terminology, structure, and relations before treating implementation as authoritative.

### 2.8 Reusable Foundations

Canon, governance, and engineering standards should be reusable by future OMSP repositories.

### 2.9 Controlled Evolution

Material changes should move through issue-backed Work Packages, reviewed PRs, and versioned artifacts.

### 2.10 Human-Governed AI Assistance

AI may assist with drafting, analysis, comparison, consistency checks, and summaries, but may not replace approval authority or invent evidence.

## 3. Application

OMSP principles should be applied when:

- defining new artifacts;
- creating Work Packages;
- reviewing PRs;
- approving baselines;
- preparing releases;
- introducing automation;
- resolving governance conflicts;
- interpreting downstream repository behavior.

## 4. Conflict Resolution

When principles appear to conflict, use the following preference order:

1. preserve human accountability;
2. preserve traceability and evidence;
3. preserve shared canon and governance consistency;
4. preserve downstream usability;
5. optimize implementation convenience.

## 5. Maintenance

These Principles are maintained through issue-backed Work Packages and reviewed pull requests. Material changes require governance review and version metadata update.
